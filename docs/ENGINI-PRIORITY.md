# חיבור Priority ⇄ OmniView דרך Engini — מסמך הטמעה

> גרסה 1.0 · 7 באוקטובר 2026 · מתאים לגרסת אפליקציה 4.8.0 ומעלה
>
> המסמך מיועד לשלושה קוראים: **מנהל המערכת ב-OmniView**, **המטמיע ב-Engini** ו**יועץ ה-Priority**.
> כל אחד מהם מוצא כאן את מה שהוא צריך כדי להתחיל.

---

## 1. התמונה בקצרה

```
             ┌──────────── כל כמה דקות, תרחיש ב-Engini ────────────┐
             │                                                      │
  Priority ──┤ ① פקודות עבודה + פעולות + סידוריים ──► POST /work-orders ──► OmniView
             │                                                      │
  Priority ◄─┤ ② דיווח ייצור על הפעולה       ◄── GET /sign-offs   ◄── OmniView
             │ ③ אישור שהדיווח נקלט           ──► POST /sign-offs/ack
             └──────────────────────────────────────────────────────┘
```

| כיוון | מה עובר | מתי |
|---|---|---|
| **Priority → OmniView** | פקודות עבודה: מק"ט, כמות, סניף, פרויקט, תאריכים, סטטוס, מסלול הפעולות, כמות מדווחת לכל פעולה, זמני תקן, מספרים סידוריים | בכל ריצה של התרחיש |
| **OmniView → Priority** | כל **חתימה על שלב** באפליקציה: איזו פק"ע, איזו פעולה, איזו יחידה (S/N) או כמה יחידות, מי עבד, מתי התחיל וסיים, כמה דקות נטו ודקות ליחידה | מהרגע שמפעילים "דו-כיווני" |

**העיקרון:** מה שמגיע מ-Engini עובר **בדיוק אותו קוד** של ייבוא קובץ ה-Excel מ-Priority שעובד היום
(אותם 35 סטטוסים, אותו קיפול שורות לפק"ע, אותו "עדכון במקום לפי מספר פק"ע"). כל מה שעובד היום עם הקובץ
עובד אותו דבר בחיבור — רק אוטומטית.

## 2. רשימת הכנה — מה צריך לפני שמתחילים

### 2.1 מצד OmniView (מנהל המערכת)

- [ ] שלבים 1–4 בסעיף 9.2 בוצעו: השרת הוכן, גרסה **4.8.0** פרוסה, והנעילה הופעלה.
- [ ] **מפתח API** ל-Engini: נוצר במסך **📂 ייבוא / ייצוא Excel ← 🔌 חיבור Priority דרך Engini ← 🔑 צור מפתח**.
  המפתח מוצג **פעם אחת בלבד** ומתחיל ב-`ov_`. העבירו אותו ל-Engini בערוץ מאובטח (לא במייל ולא בוואטסאפ).
- [ ] **שיוך פעולות לשלבים**: אם כבר ייבאתם קובץ Priority מהמחשב הזה, לחצו באותו כרטיס **⬆️ העלה את השיוך מהמכשיר הזה**.
  כך הפעולות שכבר מופו לשלבים ייפלו על אותם שלבים גם דרך Engini. פעולה חדשה שלא מופתה נפתחת כשלב חדש (כמו בייבוא קובץ).

### 2.2 מצד Priority (יועץ ה-Priority)

- [ ] **ממשק API (REST/OData) פעיל ברישיון**, וכתובת השרת, שם הסביבה (tabula.ini) וקוד החברה.
- [ ] **משתמש API ייעודי ל-Engini**:
  - קריאה: פקודות עבודה, הפעולות שלהן, המספרים הסידוריים.
  - כתיבה (לדו-כיווני בלבד): דיווח ייצור / דיווח על פעולה בפק"ע.
- [ ] **מאיפה מגיע כל שדה** בטבלה שבסעיף 4.2. הדוח שמייצאים היום ל-Excel הוא דוח מותאם. חלק מהעמודות
  (`ז.תקן ליח' בדק' למקט`, `מחיר אלת'א בש'ח`, `כמות מדווחת`, `יתרה לבצוע`) עשויות להיות מחושבות,
  וצריך לוודא שאפשר לקבל אותן דרך ה-API.
- [ ] **איך מדווחים ייצור על פעולה**: באיזה מסך/ישות, ואילו שדות חובה. למשל עובד, כמות, S/N, זמן עבודה, תאריך.
  איך **מבטלים** דיווח, ומה המזהה שחוזר מ-Priority על כל דיווח. את המזהה הזה Engini מחזיר אלינו כ-`priority_ref`.
- [ ] **מיפוי עובדים**: אם Priority דורש מספר עובד בדיווח, צריך טבלת התאמה בין שם המשתמש ב-OmniView
  (`worker_id` / `worker_name`) לבין מספר העובד ב-Priority.

### 2.3 מצד Engini (המטמיע)

- [ ] מחבר Priority מוגדר עם משתמש ה-API.
- [ ] תרחיש עם שלוש קריאות HTTP לפי סעיפים 4–6, וטיפול בשגיאות לפי סעיף 7.
- [ ] המפתח מ-2.1 שמור כסוד (Secret / Connection) בתוך Engini.

### 2.4 החלטות לקבל מראש

| נושא | המלצה |
|---|---|
| תדירות | כל 5–15 דקות בשעות העבודה |
| אילו פק"ע לשלוח | כל הפק"ע הפתוחות, או רק מה שהשתנה מאז הריצה הקודמת. שתי הדרכים בטוחות: שליחה חוזרת של אותו מידע לא משנה כלום |
| פק"ע סגורות/מבוטלות | לשלוח אותן פעם אחת כשהן נסגרות או מבוטלות, כדי שהאפליקציה תעדכן את הסטטוס |
| דו-כיווני | להפעיל רק אחרי שהכיוון הראשון רץ יציב כמה ימים |
| ייבוא Excel ידני | מותר, אבל **רק במצב "עדכן על הקיים"**. "החלף הכל" מוחק את כל הפק"ע ואת ההתקדמות שלהן |

## 4. Priority → OmniView: ‏`POST /work-orders`

### 4.1 מבנה הבקשה

**שורה לכל פעולה בפק"ע**, בדיוק כמו בדוח ה-Excel. פק"ע עם 8 פעולות נשלחת כ-8 שורות שחוזרות על נתוני הכותרת.

```json
{
  "batch_ref": "engini-2026-10-07T08:15",
  "operations": [
    { "wo": "WO-24-0153", "pn": "PN-7781", "description": "יחידת בקרה", "branch": "53",
      "project": "P-12", "qty": 10, "unit_price": 1250, "release_date": "2026-09-01",
      "end_date": "2026-11-30", "status": "בתהליך ייצור", "status_note": "",
      "op_seq": 10, "op_code": "110", "op_name": "הרכבה מכנית", "work_center": "W1",
      "reported_qty": 4, "remaining_qty": 6, "std_min_per_unit_pn": 12.5 },
    { "wo": "WO-24-0153", "pn": "PN-7781", "description": "יחידת בקרה", "branch": "53",
      "project": "P-12", "qty": 10, "unit_price": 1250, "release_date": "2026-09-01",
      "end_date": "2026-11-30", "status": "בתהליך ייצור",
      "op_seq": 20, "op_code": "120", "op_name": "בדיקה חשמלית", "work_center": "W2",
      "reported_qty": 0, "remaining_qty": 10, "std_min_per_unit_pn": 5 }
  ],
  "serials": [
    { "wo": "WO-24-0153", "pn": "PN-7781", "sn": "SN-0001" },
    { "wo": "WO-24-0153", "pn": "PN-7781", "sn": "SN-0002" }
  ]
}
```

### 4.2 השדות

| שדה JSON | חובה | העמודה בדוח Priority של היום | הערות |
|---|---|---|---|
| `wo` | ✅ | מספר פק"ע | המפתח. שורה בלי מספר פק"ע מדולגת |
| `op_name` | ✅ | תאור פעולה | הופך לשלב באפליקציה. **זה המפתח של מיפוי הפעולה לשלב** |
| `op_seq` | ✅ | שלב בפק"ע | סדר הפעולה במסלול (10, 20, 30…) |
| `status` | ✅ | סטטוס פק"ע | הטקסט כפי שהוא ב-Priority, למשל "בתהליך ייצור". מתורגם לפי המילון של האפליקציה |
| `branch` | ✅ | סניף | פק"ע בלי סניף (0 או ריק) **לא נכנסת**, כמו בייבוא הקובץ |
| `qty` | ✅ | כמות | |
| `pn` | מומלץ | מק"ט | גם המפתח של זמני התקן |
| `description` | מומלץ | תיאור מוצר | |
| `project` | | פרויקט | 0 = ללא פרויקט. פרויקט חדש נפתח אוטומטית |
| `unit_price` | | מחיר אלת'א בש'ח | |
| `release_date` | | תאריך שחרור | `YYYY-MM-DD`, או תאריך ISO מלא |
| `end_date` | | ת. סיום יצור | היעד שמולו נמדד איחור |
| `status_note` | | סיבת עיכוב / הערת סטטוס | מוצג בכרטיס פק"ע תקועה |
| `op_code` | מומלץ לדו-כיווני | פעולה | חוזר אליכם בכל חתימה כדי לדעת על איזו פעולה לדווח |
| `work_center` | | מרכז עבודה | חוזר אליכם בכל חתימה |
| `reported_qty` | מומלץ | כמות מדווחת | כמה יחידות כבר עברו את הפעולה ב-Priority |
| `remaining_qty` | | יתרה לבצוע | משמש רק כש-`reported_qty` ריק |
| `std_min_per_unit_pn` | | ז.תקן ליח' בדק' למקט | דקות תקן ליחידה. נשמר כזמן התקן של המק"ט |
| `std_min_per_unit_wo` | | ז.תקן ליח' בדק' בפקע | משמש רק כשאין תקן ברמת המק"ט |

`serials` הוא רשימה אופציונלית של המספרים הסידוריים שכבר הונפקו (`wo`, `pn`, `sn`).
פק"ע שאין לה סידוריים נכנסת ל**מעקב לפי כמות**.

> **אפשר גם לשלוח את שמות העמודות בעברית** בדיוק כמו בדוח (`"מספר פק\"ע"`, `"תאור פעולה"` וכו').
> הם נקראים באותו אופן.

### 4.3 כללים לשליחה

1. **כל הפעולות של אותה פק"ע חייבות להיות באותה בקשה.** פק"ע שהפעולות שלה נחתכו בין שתי בקשות תקבל מסלול חלקי.
2. **עד 5,000 שורות לבקשה** (מומלץ עד כ-200 פק"ע). כמות גדולה יותר מחלקים לכמה בקשות, לפי פק"ע.
3. **בקשה אחת בכל פעם לכל חברה.** בקשה שמגיעה בזמן שקודמת עוד נכתבת מקבלת `409`. ממתינים 5 שניות ושולחים שוב.
4. **שליחה חוזרת בטוחה.** אותן שורות פעמיים לא משנות כלום. התשובה השנייה תהיה `added: 0, updated: 0`.

### 4.4 מה קורה בצד OmniView

כל אצווה נכתבת **בטרנזקציה אחת**: היא נכנסת כולה, או שלא נכנס ממנה כלום.

- **פק"ע חדשה** נפתחת עם המסלול שלה, הסידוריים, ההתקדמות וזמני התקן.
- **פק"ע קיימת** מזוהה לפי מספר הפק"ע (בלי תלות ברווחים ובאותיות גדולות/קטנות), ומתעדכנים **רק השדות ש-Priority אחראי עליהם**:
  סטטוס, כמות, מחיר, פרויקט, סניף, תאריכים, תיאור, מק"ט, מסלול. סידוריים חדשים נוספים, ואף סידורי לא נמחק.
  מה שנרשם ברצפה נשאר כמו שהוא: תקלות, חוסרים, אספקות ודיווחי העובדים.
- **פק"ע שלא השתנתה לא נכתבת בכלל**, ולכן אצווה של אלפי פק"ע עוברת כמעט בלי עומס.
- **מדולגות**, כמו בייבוא הקובץ: פק"ע בסטטוס "פקע COC", פק"ע בלי סניף, ופק"ע מבוטלת שלא קיימת עדיין באפליקציה.
  פק"ע קיימת שבוטלה ב-Priority מסומנת כמבוטלת ומוסתרת.

### 4.5 התשובה

```json
{
  "ok": true, "inbox_id": 41,
  "added": 3, "updated": 12, "unchanged": 185, "cancelled": 1,
  "new_serials": 20, "progress_changed": 9, "new_stages": 0, "new_projects": 1,
  "logs_written": 36, "logs_dropped": 4, "requeued_sign_offs": 0,
  "skipped": { "closed": 0, "coc": 2, "cancelled": 0, "no_branch": 1 },
  "changes": [ { "wo": "WO-24-0153", "fields": ["סטטוס פק\"ע", "התקדמות"], "from": "שוחררה", "to": "בתהליך ייצור" } ],
  "issues":  [ { "level": "info", "msg": "2 פק\"ע בסטטוס פקע COC לא יובאו" } ]
}
```

כל אצווה מופיעה גם באפליקציה, בכרטיס 🔌, עם השעה וכמה פק"ע נוספו או עודכנו.

### 4.6 למה לא ייווצרו כפילויות

| שכבה | מה היא מבטיחה |
|---|---|
| התאמה לפי מספר פק"ע | פק"ע קיימת מתעדכנת במקום. אותו קוד כמו "עדכן על הקיים" בייבוא הקובץ |
| **אינדקס ייחודי במסד** (חברה + מספר פק"ע) | המסד עצמו מסרב לשורה שנייה עם אותו מספר, **מכל מקור**: Engini, ייבוא Excel או הקלדה ידנית |
| נעילה לכל חברה | שתי אצוות לא נכתבות במקביל, כך ששלב חדש לא נפתח פעמיים |
| טרנזקציה אחת לאצווה | אין חצי-אצווה. אצווה שנכשלה פשוט נשלחת שוב |
| רשומות ההתקדמות של Priority | רק הן מוחלפות בכל עדכון. דיווח של עובד לא נמחק לעולם |

## 5. OmniView → Priority: ‏`GET /sign-offs`

פעיל רק אחרי שמסמנים באפליקציה **"דו-כיווני: שליחת חתימות שלבים חזרה ל-Priority"**.
עד אז הרשימה תמיד ריקה, ושום דבר לא נצבר.

### 5.1 מתי נוצר אירוע

| מה קרה באפליקציה | האירוע |
|---|---|
| עובד **חתם על שלב** (יחידה אחת, קבוצת יחידות או כמות) | `sign` |
| חתימה **בוטלה**: נמחקה, נפתחה מחדש, או בוצע ↩️ אחזור | `unsign`, עם `reverses_event_id` ו-`priority_ref` של הדיווח המקורי |
| חתימה שונתה (זמן, יחידה, שלב) אחרי שכבר דווחה | `unsign` על הישנה ואחריו `sign` חדש |
| חתימה בוטלה **לפני** ש-Engini אסף אותה | שום דבר לא נשלח. האירוע פשוט מבוטל |

התקדמות שהגיעה **מ-Priority** (משתמש "ייבוא Priority") **לעולם לא נשלחת חזרה**.

### 5.2 מבנה האירוע

```json
{
  "ok": true, "two_way": true,
  "events": [
    {
      "event_id": 812, "type": "sign", "attempt": 1, "created_at": "2026-10-07T08:50:03Z",
      "work_log_id": "k3j2h1a",
      "wo_number": "WO-24-0153", "pn": "PN-7781",
      "operation": { "code": "110", "seq": 10, "name": "הרכבה מכנית", "work_center": "W1" },
      "stage_id": "s1", "stage_name": "הרכבה מכנית",
      "serial_number": "SN-0003", "quantity": 1,
      "worker_id": "u7", "worker_name": "דנה לוי",
      "start_time": "2026-10-07T08:00:00Z", "end_time": "2026-10-07T08:50:00Z",
      "duration_min": 42, "pause_min": 8, "minutes_per_unit": 42,
      "group_id": null, "group_size": 1
    }
  ]
}
```

| שדה | משמעות |
|---|---|
| `event_id` | מזהה ייחודי. **מפתח אידמפוטנטיות**: אירוע עשוי להגיע יותר מפעם אחת, ואסור לדווח אותו פעמיים |
| `type` | `sign` = לדווח · `unsign` = לבטל את הדיווח שמזוהה ב-`priority_ref` |
| `operation` | הפעולה ב-Priority שעליה מדווחים: הקוד (`op_code`), השלב בפק"ע (`op_seq`) ומרכז העבודה, כפי שהגיעו מ-Priority |
| `serial_number` / `quantity` | יחידה אחת לפי S/N, או כמות יחידות (פק"ע שמנוהלת לפי כמות) |
| `duration_min` | דקות עבודה **נטו**, בלי הפסקות ו-HOLD |
| `minutes_per_unit` | הזמן ליחידה. בעבודה על קבוצת יחידות יחד (`group_size` > 1) הזמן מתחלק ביניהן |
| `start_time` / `end_time` | UTC בפורמט ISO-8601 |

### 5.3 כללי איסוף

- האירועים מגיעים **בסדר יצירתם**, ויש לדווח אותם באותו סדר. `unsign` תמיד אחרי ה-`sign` שהוא מבטל.
- אירוע שנמסר ל-Engini לא יימסר שוב **10 דקות**. אם לא אושר בזמן הזה, הוא חוזר (מסירה at-least-once).
- `limit` עד 500 לבקשה. אוספים עד שהרשימה ריקה.

## 6. ‏`POST /sign-offs/ack`

אחרי כל דיווח ל-Priority, לאשר:

```json
{ "acks": [
  { "event_id": 812, "ok": true,  "priority_ref": "<המזהה שחזר מ-Priority על הדיווח>" },
  { "event_id": 813, "ok": false, "error": "Priority: הפק\"ע סגורה לדיווח", "retry": false },
  { "event_id": 814, "ok": false, "error": "timeout", "retry": true }
]}
```

| מקרה | מה לשלוח | מה קורה |
|---|---|---|
| הדיווח נקלט | `ok: true` + `priority_ref` | האירוע מסומן "נקלט ב-Priority". ה-`priority_ref` יחזור ב-`unsign` אם החתימה תבוטל |
| תקלה זמנית (רשת, נעילה) | `ok: false, retry: true` | האירוע חוזר לתור ויימסר בריצה הבאה |
| דחייה עניינית | `ok: false, retry: false, error: "…"` | מסומן "נכשל". השגיאה מוצגת למנהל באפליקציה, ויש שם כפתור "🔁 שלח שוב" |

### 6.1 למה התקדמות לא נספרת פעמיים

אחרי שהאפליקציה מדווחת ל-Priority, ה"כמות המדווחת" ב-Priority **כוללת** את החתימות של האפליקציה.
כשהיא חוזרת באצווה הבאה, האפליקציה מורידה ממנה את מה שהיא עצמה דיווחה ו-Priority אישר. רק ההפרש,
כלומר מה שדווח ישירות ב-Priority, נרשם כהתקדמות "ייבוא Priority", ועל יחידות שאף עובד לא חתם עליהן.

**דוגמה:** בפק"ע של 10 יחידות, Priority מדווח 4 על פעולה 10. מתוכן יחידה אחת חתמה דנה באפליקציה, והדיווח שלה אושר.
האפליקציה רושמת 3 יחידות כ"ייבוא Priority", ועוד יחידה אחת של דנה. סך הכל 4 ולא 5.

## 8. תרחיש מומלץ ב-Engini ודוגמאות

**בכל ריצה (כל 5–15 דקות):**

1. **קודם החוצה:** `GET /sign-offs?limit=200` → לדווח כל אירוע ל-Priority → `POST /sign-offs/ack`. חוזרים עד שהרשימה ריקה.
2. **אחר כך פנימה:** לשלוף מ-Priority את הפק"ע (פתוחות, או שהשתנו מאז הריצה הקודמת) עם הפעולות והסידוריים →
   `POST /work-orders` באצוות לפי פק"ע.

הסדר חשוב: כשהאישורים נשלחים לפני שמושכים את הכמויות, ספירת היחידות מדויקת כבר באותה ריצה.

```bash
KEY='ov_…'   # מהכרטיס 🔌 באפליקציה
BASE='https://lwiurzkiojctwzllpnmr.supabase.co/functions/v1/erp'

curl -s "$BASE/health" -H "x-api-key: $KEY"

curl -s -X POST "$BASE/work-orders" -H "x-api-key: $KEY" -H 'content-type: application/json' \
  -d '{"batch_ref":"test-1","operations":[{"wo":"TEST-1","pn":"PN-1","branch":"53","qty":2,
       "status":"שוחררה","op_seq":10,"op_code":"110","op_name":"הרכבה מכנית"}]}'

curl -s "$BASE/sign-offs?limit=50" -H "x-api-key: $KEY"

curl -s -X POST "$BASE/sign-offs/ack" -H "x-api-key: $KEY" -H 'content-type: application/json' \
  -d '{"acks":[{"event_id":1,"ok":true,"priority_ref":"R-1"}]}'
```

### 8.1 בדיקות קבלה לפני עלייה לאוויר

- [ ] `/health` מחזיר את החברה הנכונה.
- [ ] אצווה של 3–5 פק"ע אמיתיות → מופיעות באפליקציה עם מסלול, סטטוס, סידוריים והתקדמות **זהים** למה שמתקבל מייבוא קובץ ה-Excel של אותן פק"ע.
- [ ] אותה אצווה שוב → `added: 0, updated: 0`. אין כפילויות ברשימת הפק"ע.
- [ ] שינוי סטטוס ב-Priority → אחרי הריצה הבאה הסטטוס התעדכן, והתקלות שנרשמו באפליקציה נשארו.
- [ ] (דו-כיווני) חתימה על שלב באפליקציה → מופיעה ב-`/sign-offs` עם הפעולה הנכונה → מדווחת ב-Priority → `ack`.
  בריצה הבאה ההתקדמות באפליקציה לא גדלה פעמיים.
- [ ] (דו-כיווני) מחיקת החתימה באפליקציה → `unsign` עם ה-`priority_ref` → הדיווח מבוטל ב-Priority.
